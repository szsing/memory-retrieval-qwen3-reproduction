# InMind 全量优先实验：协议与复现边界

本轮先完成一个核心 benchmark：InMind 全部 125 题。LUCid / ImplexConv 原有本地材料不是完整官方评测历史，暂不把裁剪版本称为全量。

## 数据核对

- InMind 固定源码 commit `5a2ab2686d3d5b832575f0288d41ecc93eab358b`，官方发布校验脚本已通过。任务 SHA-256 与之前下载版本一致。
- 125 个任务，47 个背景会话、486 轮背景。逐题将目标 user/assistant 两轮插在第九会话末尾，再处理其后 38 个会话。每题总计 488 轮。
- 每个会话按连续 user/assistant 交互分块，保留全部角色及原文、不跨会话、不做 600/1000 字符裁剪，共 247 块/题。此分块属于受控适配；不是官方 stateless control 的 487 块配置。
- 系统输入只包含角色和内容；explanation/relation/provenance 等标签不参与生成属性、写入、检索或回答。评分器可以读取官方评分字段。
- 某些任务复用了同一个用户事实。保留官方全部题目，同时在统计中记录事实关联，不把它们当作无关联的独立用户样本。
- LUCid 现有 `lucid.json` 为 1,936 个 query 的 latent_sessions；官方 C/S/B/L 文件另有 haystack_sessions。原来的 120/240 子集加共享干扰历史不是官方全量设置。
- ImplexConv 现有文件仅抽取 30+30 用户，保留证据及 30 个其他会话，且只保留用户发言并裁剪字符。旧下载 API 响应报告 opposed 数据共 1,550 行；仍需下载并核对完整历史及其官方评测脚本。

## 控制条件

生成模型固定 Qwen3-8B，revision `b968826d9c46dd6066d109eabc6255188de91218`，BF16，non-thinking，temperature=0，seed=42。为了保留长历史片段，将服务接受的输入+输出上限从 8192 扩到 32768；没有修改权重或启用 RoPE 扩展。用六段最长实际记忆检查了超过 8K 的输入，显存峰值约 17.2 GiB。单次输出上限仍为 2048。超限/截断报错，不静默丢弃输入或样本。

Embedding 统一使用固定版本 BGE-small、CPU；本轮统一使用编码器原始 query 编码，不加额外 query prefix，以对齐两个基线的原生 Hugging Face 编码方式。模型自带的 embedding token 长度限制仍存在；这与把历史文本直接裁剪不同，应在结果中披露。

检索基础 top-k=6；实际回答上下文上限 4096 个 Qwen token，按完整记忆边界加入。A-MEM 保留原生链接邻居扩展，随后应用相同 token 预算，不能把它的 six seeds 当成 six total memories。

RRF 常数 60、属性权重 2。对相同分数使用平均秩，避免无属性的全零分数因存储顺序获得不同加分。候选排序和融合均发生在本题状态内部。Picker 未选满时按本方法的基础排名回填，不混入另一方法的排序。

本轮正式协议中每次 LLM 请求只处理一条记忆或一个问题；不把不同任务、直接与间接查询放进同一个生成 batch，避免跨任务及对照问题的信息影响。之前批量处理的生成结果只作适配诊断，正式运行仅复用输入完全相同的单条请求缓存。

本地服务不做强制语法解码。适配层在系统消息中附带输出 schema，并在生成后校验；批量条目缺失时拆批，仍失败则中止。单条对象可规范化为单元素批次。该格式适配不根据评测标签修改模型内容。

属性生成仅读取每个交互块的用户发言；纯助手块属性为空。完整 user/assistant 原文仍用于所有方法的检索与实际上下文。先前整对文本生成属性的消融属于适配诊断，保存在 retrieval-pair-properties-pretest-audit，未作为正式方案选择结果；修正在查看保留集评分前完成。

## 先消融再冻结

使用原项目学习域、原始 task_id 哈希顺序的前 40 题，每题间接和直接查询各一次：

1. Dense；HyDE（沿用原项目的原查询与虚拟记忆向量混合实现）。
2. 只展开记忆侧属性；只展开查询侧属性；双侧展开。
3. 本题池内打乱记忆属性对应关系。
4. 双侧属性+gate+基础检索首条保留。
5. 再加入 LLM picker。

在双侧、gate/pin、picker 三个候选中，以开发集间接+直接 Hit@6 总和选择，平分偏向更简单版本。权重和 prompt 不搜索。写入 `retrieval/recipe.lock.json` 后才处理其余 85 题查询。

全 125 题结果是描述性结果；85 题是相对本轮选择过程的分离评测，61 个未见领域题单独报告。历史 Haiku 设计搜索已经看过部分数据，不能把整个 benchmark 宣称为从未见过。

## Mem0 与 A-MEM 的来源与适配

- Mem0 固定官方 PyPI `mem0ai==0.1.98`，为 2025-05-09 的论文时期发布版本。保留原生事实抽取、ADD/UPDATE/DELETE/NONE 决策、Qdrant 检索。不是最新版 2.2.1 的 additive extraction 路径。固定 Qdrant client 1.13.3，以匹配该版本的 search API。
- A-MEM 使用官方指向的论文实验仓库 `WujiangXu/AgenticMemory`，源码 commit `f9a173dec325d84fcc97e7828775c7b241c33466`。保留 note 分析、链接、邻居演化、论文模式的定期合并以及原生链接展开检索；检索前执行实验脚本中原样提取的 generate_query_llm 关键词生成方法，不省略该步骤。`refresh_index=False`，未擅自切换到改善版本。
- 适配 A-MEM 的 encoder provider 固定 BGE-small/CPU；合并时向其配置读取接口返回这个固定模型名，避免上游兼容回退静默改成 MiniLM。最小检查还会强制执行一次合并并验证模型名。
- 两者均通过适配层使用同一台本地 Qwen 服务，不调用付费 API；没有把两者重写成普通摘要检索。
- A-MEM 的 note timestamp 使用固定、按输入顺序递增的逻辑时钟，保证复现；原文中的日期不改。这不是对原始事件日期的重建。
- 每题从独立状态处理完整时间线；查询共享冻结的最终状态，查询前后做状态摘要检查。未完成的旧状态移到 interrupted 目录后重新构建，不把中断后重放混成一条时间线。
- 两条已知事实的真实写入/检索检查，以及原生错误计数、JSON 解析与更新错误检查必须通过。官方代码吞掉的异常会令本轮中止，不能算作得零分的合法运行。
- 这是**官方开源代码的本地模型受控适配**，不是原论文模型、超参数和数值的逐项复刻。版本、源码/运行脚本、环境和适配差异均保留。

## 输出与评测

先记录检索 Hit@1/3/6、MRR、实际上下文及 token 数。由于 Mem0 会改写记忆，不能只用原始 target 行号判断它是否找回事实；另外使用官方 target-recall prompt 对实际上下文做语义检查。

完整基线成功后，队列会使用官方 answer/judge prompts 生成本地回答与评分，保存每题原始上下文、回答、评分理由，并运行官方 submission 格式/覆盖验证器。所有回答及 judge 都使用本地 Qwen，因此属于同骨干模型的开发性端到端评测；不能标为使用官方 gpt-5-mini 的 leaderboard 复现。后续还需独立 API judge 或人工一致性检查。

队列在服务器 `/root/autodl-tmp/memory-retrieval-indirect-requests/experiments/full-run-v1`，阶段状态见 `queue-status.tsv`，日志为 `retrieval.log`、`mem0-full.log`、`amem-full.log`、`answers.log`。基线失败会留下明确退出状态，不静默跳过任务，也不会把不完整结果写成全量完成。
