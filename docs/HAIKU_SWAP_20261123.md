# Haiku 属性替换诊断：61 题检索对照

日期：2026-11-23。此实验已完成；没有恢复此前暂停的其他 benchmark。

## 设置与核对

使用原始脚本的 InMind testB 全部 61 个 unseen-domain 请求，在同一个 365 条共享记忆库（240 条背景、125 条事实）中检索。它覆盖该脚本的 61 题子集，不代表整个 InMind 的全量评测。缓存中的记忆文本、顺序、请求和目标索引均逐条对齐，重复文本保留原始索引。目标标签不参与检索。

Qwen3-8B BF16、vLLM 0.11.0、关闭 thinking、temperature=0、max_tokens=2048、BGE-small-en-v1.5、原版 PV2 prompt、属性权重 8、wide picker（dense 前12与join前6的并集）均保持原有设置。沿用已修复的严格输出格式适配器。HyDE、gate 输出在各组之间冻结；picker 始终为 Qwen，并按实际候选列表调用或命中完全相同请求的缓存。

Haiku 仅提供已经生成的属性缓存，本次没有调用 Haiku API。

## 结果

主指标是目标事实在整个 365 条记忆中的最终前6名。另记录源脚本 off-style 指标：最终打分后仅计算240条背景中有多少条高于目标。这一辅助指标仍使用365条库生成候选，不等同于真正单独运行241条候选库。

| 记忆侧属性 | 请求侧属性 | 全库 Hit@6 | off-style | picker 候选覆盖目标 |
|---|---|---:|---:|---:|
| Qwen | Qwen | 7/61 | 13/61 | 8/61 |
| Haiku | Qwen | 8/61 | 17/61 | 10/61 |
| Qwen | Haiku | 5/61 | 13/61 | 12/61 |
| Haiku | Haiku | 11/61 | 29/61 | 16/61 |
| Haiku | 原始请求（仅写侧） | 7/61 | 17/61 | 11/61 |
| Haiku | 仅属性有无，删除语义匹配分数 | 3/61 | 7/61 | 3/61 |
| Haiku | Haiku 请求属性固定循环错配 | 4/61 | 13/61 | 4/61 |

无属性的 plain dense 基线命中 1/61，与预期一致。相同文本命中与索引命中的汇总数一致。

## 能得出的结论

1. 不能把问题归结为“只有记忆侧写得不好”。单换记忆侧仅从7升到8；单换请求侧最终从7降到5；两侧一起换升到11。提升主要表现为两侧配合。2×2交互的描述性净差为11−8−5+7=5题，尚未建立稳定交互效应。
2. 请求侧并非没有改善召回。只换请求侧时，目标进入picker候选的次数从8升到12，但其中7题最终未进入前6。只看最终5/61，容易把候选选择阶段的损失误认成请求属性完全无效。双侧Haiku时16题进入候选、11题最终命中，仍有5题在后续阶段丢失。
3. 正确语义对应有贡献迹象：双侧Haiku的11高于仅写侧7、属性有无3、错配4。它超过了简单“有属性就是重要事实”的解释。但61题规模下，还不能声称双侧方案稳定优于仅写侧或原配置。
4. 后续已核实：服务器保存的原仓库commit d62aa408a4e0b9515eed9313663a025a07b08497，bench_runs.jsonl中2026-11-17 11:31的wide记录同时报告inmind_off=[32,61]和inmind_dense=[19,61]。因此同口径应比较off-style的32→29、全库Hit@6的19→11，不能比较32与11。原仓库相关文件工作区未改动。详情见HAIKU_PICKER_AUDIT.md和results/haiku-swap-20261123-v1/protocol-picker-audit.json。

配对命中变化：双侧Haiku相对Qwen/Qwen新增6题、丢失2题，净增4题；相对仅写侧新增5题、丢失1题。精确配对二项检验（双侧，未做多重比较校正）分别p=0.2890625、p=0.21875；对属性有无p=0.0078125、错配p=0.0390625。原始值见analysis.json；这些是探索性比较，不能把未校正值当成多项检验后的确证。
